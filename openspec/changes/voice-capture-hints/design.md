# Design

## Context

입력 처리는 `src/http/intake.ts`가 주소의 옵션(`async`, `format`, `dry`, `quality`)을 읽어 해석 단계에 넘기고, 해석 프롬프트는 `src/domain/interpret.ts`가 만든다. 시각은 설계 결정 5에 따라 벨루 메모 첫 줄에 `15:00` 형식으로 적고 마감일 필드에는 날짜만 둔다. 보고는 `classifyOpenTasks`(`src/domain/report.ts`)가 오늘, 임박, 밀린 일, 마감 없음으로 나누는데, 오늘 항목만 메모를 함께 넘기고 임박 항목은 이름, 마감, 남은 일수만 넘긴다. 동기는 proposal.md의 Why를 본다.

## Goals / Non-Goals

**Goals:**
- 받아쓰기 입력의 오인식을 모델이 임의로 고쳐 확정하지 않게 한다.
- 약속 시각을 아침 보고에서 `[오늘]`과 `[임박]` 모두에서 볼 수 있게 한다.
- 기존 단축어와 서버 입력 계약은 그대로 둔다.

**Non-Goals:**
- 시각을 벨루의 별도 필드로 저장하거나 시각에 맞춰 알리는 것.
- 받아쓴 글을 사람이 확인·수정하는 화면(단축어가 알림에 받아쓴 글을 보여 주는 것으로 대신한다).
- `[먼저 할 일]`과 `[밀린 일]`의 시각 표시. 순위 문장이 이미 길고, 밀린 일은 시각이 의미가 작다.

## Decisions

### 1. 음성 표시는 주소의 `source=voice` 옵션이다
기존 옵션과 같은 방식이다. 단축어는 주소 끝에 `&source=voice`만 붙이면 되고 JSON 본문 계약은 바뀌지 않는다. `voice`가 아닌 값은 무시한다(`quality`와 같은 규칙). 대안은 본문에 `source` 필드를 넣는 것인데, 본문 계약을 바꾸게 되어 기존 클라이언트와 구분이 어려워진다.

### 2. 받아쓰기 규칙은 표시가 있을 때만 프롬프트에 붙인다
받아쓰기 텍스트는 구두점이 없고 이름과 장소가 틀릴 수 있다고 알린다. 의심스러운 고유명사는 **고쳐 쓰지 않고 보이는 그대로** 이름에 쓰고, `assumptions`에 "받아쓰기 오인식 가능: …"을 짧게 적는다. 의심이 없으면 적지 않는다. 이유: 모델이 그럴듯한 이름으로 바꿔 쓰면 틀린 이름이 맞아 보이는 채로 확정되어 알아채기 어렵고, 비서에는 태스크 수정 도구가 없다. 표시가 없으면 프롬프트는 지금과 같다.

### 3. 시각은 메모 첫 줄에서 한 곳의 함수로 뽑는다
메모 첫 줄이 `H:MM` 또는 `HH:MM`으로 시작하면 그것이 시각이다(`report.ts`의 함수 하나). 벨루에 시각 필드가 없어서 결정 5의 메모 규약을 그대로 쓴다. `[오늘]`에서 지금처럼 메모 첫 줄을 이름 옆에 보여 주는 동작은 유지하고(장소 등도 같이 보인다), 정렬에만 이 함수를 쓴다.

### 4. 임박 항목에도 시각을 싣는다
`classifyOpenTasks`의 `upcoming` 항목에 `time`(없을 수 있음)을 추가하고, 보고 입력과 `[임박]` 줄에서 `이름(10/11 14:00·3일 후)`처럼 날짜 옆에 시각을 쓴다. 시각이 없으면 지금과 같은 줄이다.

### 5. `[오늘]` 정렬은 안정 정렬이다
시각이 있는 항목을 이른 순서로 앞에 두고, 시각이 없는 항목은 입력 순서를 유지하며 뒤에 둔다. 같은 시각끼리도 입력 순서를 유지한다.

## Risks / Trade-offs

- **모델 동작은 테스트로 완전히 확인할 수 없다.** 오인식 안내가 너무 자주 붙거나(소음) 아예 안 붙을 수 있어서, 단위 테스트는 프롬프트에 규칙이 붙는지만 확인하고 실제 모델 시험(`npm run test:live`)으로 어색한 입력과 평범한 입력을 둘 다 본다.
- 메모 첫 줄이 시각이 아닌 다른 글이면 시각이 없는 것으로 본다. 사용자가 벨루에서 직접 쓴 메모 형식에 의존하는 한계가 있다.
- 임박 줄이 시각 때문에 조금 길어져 말풍선 분량이 줄 수 있다. 구역 단위 말풍선 한도 안에서 항목 수 제한(5개)은 그대로 둔다.
