# Tasks

## 1. 사전 확인과 결정

구현 방향을 가르는 미정 사항을 먼저 확정한다. 결과는 `design.md`의 해당 결정/열린 질문에 반영한다.

- [ ] 1.1 언어/런타임과 호스팅 위치를 정해 `design.md`에 기록한다. 검증: 선택한 환경에서 "hello" 엔드포인트가 인터넷에서 호출되고, 외부 스케줄러가 그 주소를 정해진 시각에 호출하는 것을 로그로 확인한다
- [ ] 1.2 벨루에 비서 전용 계정으로 비브라우저 로그인해 세션을 얻고 태스크 생성 API를 한 번 호출해 본다. 검증: 호출한 태스크가 벨루 화면에 나타나며, 성공하면 `design.md` 결정 3을 확정하고, 막히면 대체 경로(Supabase 직접 쓰기)로 바꾼다고 기록한다
- [ ] 1.3 Gmail 읽기 전용(`gmail.readonly`) 인증을 개인 계정에 연결한다. 검증: 최근 메일 제목 5개를 읽어 출력하고, 쓰기·발송 호출은 권한 오류로 거부되는 것을 확인한다
- [ ] 1.4 카카오 나에게 보내기 앱을 등록하고 토큰 발급·갱신 절차를 확인한다. 검증: 테스트 메시지가 내 카톡에 도착하고, 만료시킨 토큰이 갱신 절차로 복구되는 것을 확인한다

## 2. 기반: 설정, 처리 이력, 위임 정책

- [ ] 2.1 비밀값과 설정(공유 비밀값, 벨루 계정, Gmail·카카오 인증, 실행 시각, 메일 키워드)을 환경에서 읽는 구조를 만들고, 비밀값은 저장소에 커밋되지 않게 한다. 검증: 값이 없으면 시작 시 어떤 항목이 없는지 알려 주며 실패하고, `git status`에 비밀값 파일이 잡히지 않는다
- [ ] 2.2 처리 이력 저장소(출처 종류, 출처 ID, 처리 시각, 결과)를 만들고 중복 조회·기록 함수를 테스트와 함께 구현한다. 검증: 같은 출처를 두 번 기록하면 두 번째가 "이미 처리됨"으로 판별되는 테스트가 통과한다
- [ ] 2.3 `delegation-policy` 구현: 모델에 노출할 도구를 위임 단계(자유/알리고 수행/확인 후 제안/금지)별로 구성한다. 수정·삭제는 제안 기록 도구로만 주고, 발송·제출 도구는 만들지 않는다. 검증: 도구 목록에 금지 단계 도구가 없다는 테스트와, 수정 요청이 실제 쓰기 없이 제안으로만 남는 테스트가 통과한다
- [ ] 2.4 위임 단계별 허용 행동 목록을 문서로 남긴다(`docs/delegation.md`). 검증: 문서의 단계별 도구 목록이 2.3의 코드 구성과 일치하는지 대조해 확인한다

## 3. 입력 접수 (`quick-capture-intake`)

- [ ] 3.1 입력 엔드포인트와 공유 비밀값 검증을 구현한다. 검증: 비밀값 없음·불일치 요청이 거부되고 모델 호출이 일어나지 않는 테스트와, 올바른 비밀값이 통과하는 테스트가 통과한다
- [ ] 3.2 텍스트 입력 해석(이름, `YYYY-MM-DD` 마감, 우선순위, 시각을 메모로)을 구조화 출력으로 구현한다. 검증: 스펙의 "다음 주 화요일 3시 랩미팅", "급함", 날짜 없는 입력 시나리오를 테스트 케이스로 만들어 통과한다
- [ ] 3.3 상대 날짜를 요청 시각과 시간대 기준 가장 가까운 미래로 해석한다. 검증: 요일·"이번 주 안에"를 기준 날짜를 고정해 시험하는 테스트가 통과한다
- [ ] 3.4 이미지 입력 해석 경로를 추가한다. 검증: 일정이 보이는 샘플 이미지에서 항목이 추출되고, Siri 입력창이 아래에 찍힌 실제 화면 이미지로도 시험해 결과를 기록한다
- [ ] 3.5 불확실한 입력은 되묻지 않고 추정하되 추정 내역을 포함한 한 문장 응답을 반환한다. 검증: 날짜 없는 입력의 응답에 "마감 없음으로 처리"가 포함되는 테스트가 통과한다
- [ ] 3.6 아이폰 단축어(Siri 음성·텍스트, 필요 시 화면 캡처)가 3.1 엔드포인트를 호출하고 응답을 보여 주게 만든다. 설정 방법은 `docs/shortcut.md`에 적는다. 검증: Siri로 한 문장을 말해 벨루에 태스크가 생기고 응답이 화면에 나타나며, 문서의 절차를 처음부터 따라 해도 같은 결과가 나온다

## 4. 장부 반영 (`ledger-task-sync`)

- [ ] 4.1 1.2에서 확정한 경로로 벨루 태스크 생성을 구현하되, 비서 표식과 출처 ID를 메모에 남긴다. 검증: 생성된 태스크의 메모에 표식과 출처 ID가 있고 벨루 화면에 정상 표시되는 것을 확인한다
- [ ] 4.2 처리 이력(2.2)을 확인해 같은 출처 중복 생성을 막는다. 검증: 같은 출처로 두 번 실행해도 태스크가 하나만 생기는 테스트가 통과한다
- [ ] 4.3 사용자가 삭제한 태스크가 되살아나지 않게 한다. 검증: 비서가 만든 태스크를 벨루에서 지운 뒤 다시 실행해도 재생성되지 않는 것을 시험한다
- [ ] 4.4 표식 없는 태스크는 수정·삭제하지 않고 불일치만 제안으로 기록한다. 검증: 마감이 다른 기존 태스크가 변경되지 않고 제안 기록만 남는 테스트가 통과한다
- [ ] 4.5 쓰기 실패 시 성공/실패를 구분해 결과에 담는다. 검증: 세 항목 중 하나를 실패시킨 시험에서 결과가 성공 2, 실패 1로 구분되는 테스트가 통과한다

## 5. 메일 선별 (`mail-triage`)

- [ ] 5.1 키워드·기간 필터와 제목/발신자/요약 기반 1차 중요도 판단을 구현한다. 검증: 키워드에 걸리지 않은 메일의 본문은 읽지 않고 모델에도 전달되지 않는 테스트가 통과한다
- [ ] 5.2 중요 판단된 메일에 한해 본문을 읽고 마감을 추출하며, 불명확하면 "불확실"로 표시한다. 검증: 날짜가 명확한 메일과 모호한 메일 샘플에서 각각 마감 추출, 불확실 표시가 나오는 테스트가 통과한다
- [ ] 5.3 처리한 메일 ID를 이력에 기록해 재처리를 막고, 결과를 `ledger-task-sync`로 넘겨 태스크를 만든다. 검증: 같은 기간을 두 번 조회해도 두 번째에는 이미 처리한 메일이 제외된다
- [ ] 5.4 실제 최근 한 달 메일로 키워드 목록과 조회 기간을 시험해 정하고, 읽기 전용 드라이런(쓰기 없음)으로 후보와 판단을 출력한다. 검증: 실제로 놓치면 곤란했던 메일이 후보에 올라오는지 눈으로 확인해 목록을 `docs/mail-keywords.md`에 기록한다

## 6. 아침 보고 (`daily-report`)

- [ ] 6.1 오늘 일정·마감, 직전 실행 이후 비서가 추가한 태스크, 불확실·불일치·실패 항목을 모아 보고 내용을 구성한다. 검증: 추가한 날/처리할 것이 없는 날 시나리오의 보고 내용이 스펙대로 나오는 테스트가 통과한다
- [ ] 6.2 카톡 나에게 보내기로 전송하고 길이 한도를 넘으면 중요 항목 우선·생략 개수 표시로 줄인다. 검증: 항목이 많은 입력에서 잘리지 않고 생략 개수가 표시되는 테스트와, 실제 카톡 수신 확인이 통과한다
- [ ] 6.3 토큰 만료 등 전송 실패를 기록하고 다음 실행에서 복구를 시도한다. 검증: 만료시킨 토큰으로 실행해 실패가 기록되고 다음 실행에서 갱신 후 전송되는 것을 확인한다
- [ ] 6.4 외부 스케줄러가 정해진 시각에 메일 선별과 보고를 순서대로 호출하게 연결하고 운영 방법을 `docs/operations.md`에 적는다. 검증: 설정한 시각에 사람 개입 없이 보고가 도착하고, 문서의 끄기·롤백 절차(비서 표식 태스크 삭제, 스케줄러·단축어 끄기)가 실제로 동작한다

## 7. 통합 확인

- [ ] 7.1 이틀 동안 실제로 사용하며 입력→벨루 반영→아침 보고 흐름이 이어지는지 확인한다. 검증: 이틀간 입력한 항목과 메일에서 찾은 항목이 모두 보고에 나타나고, 잘못 들어간 태스크를 삭제해도 되살아나지 않으며, 결과를 `docs/operations.md`에 기록한다
