# Design

## Context

동기와 범위는 `proposal.md`, 요구사항은 `specs/`를 본다. 설계에 영향을 주는 현재 사실만 적는다.

- **벨루**(`/Users/joon/CODINGPROJECT/veloo/veloo.2joon.com`, 이 change에서 수정하지 않음): `todos` 테이블은 `name`, `memo`, `priority`, `deadline`(텍스트, `YYYY-MM-DD`면 화면에 `M/D`로 표시), `done`을 가진다. 시각 필드는 없다. 백엔드는 쿠키 세션 로그인(`sessions` 테이블)을 쓰고 서버 키로 Supabase에 접근한다. 프론트엔드가 호출하는 태스크 생성 API가 있다.
- **카톡 "나에게 보내기"**: 보내기만 가능하다. 읽기는 불가능하므로 입력 채널이 될 수 없다.
- **입력은 사람이 해야 한다**: 머릿속 일정은 컴퓨터가 알 수 없다. 설계 목표는 입력을 없애는 것이 아니라 한 문장 말하기 수준으로 줄이고, 스스로 도착하는 정보(메일)는 비서가 가져오는 것이다.
- 이 폴더(`1111`)는 빈 저장소에서 시작한다. 언어·호스팅은 아직 정하지 않았다.

## Goals / Non-Goals

**Goals:**
- 입력(단축어), 메일, 장부(벨루), 보고(카톡)를 서로 교체 가능한 어댑터로 분리한다.
- 모델의 판단이 틀려도 장부가 오염되거나 되살아나지 않도록 쓰기 경계를 구조로 강제한다.
- 각 기능에 필요한 만큼의 자율성만 쓴다(아래 결정 1).

**Non-Goals:**
- 범용 에이전트 프레임워크. 이 비서 하나에 맞춘 최소 구조만 둔다.
- 사용자 인터페이스(웹 화면). 사용자 접점은 단축어, 벨루, 카톡뿐이다.
- 여러 사용자 지원. 한 명(작성자)의 계정만 가정한다.

## Decisions

### 1. 기능별로 자율성의 크기를 다르게 둔다

| 기능 | 형태 | 이유 |
|---|---|---|
| 입력 해석 | 모델 한 번 호출(구조화 출력) | 입력→필드 추출은 순서가 고정이다. 도구 루프가 필요 없다 |
| 메일 선별 | 도구를 쥔 루프 | 후보 목록, 본문 열람, 필요 시 추가 조회 사이에서 모델이 다음 행동을 고른다. 여기만 진짜 에이전트 구간이다 |
| 보고 | 코드로 내용을 모으고 모델은 문장만 다듬음 | 수집은 결정적이다. 모델에게 맡길 이유가 없다 |

대안은 전부 에이전트 루프로 만드는 것이었으나, 입력과 보고에서는 비용과 불안정성만 늘고 얻는 게 없어 채택하지 않았다.

### 2. 호출 구조: 상태 없는 HTTP 서비스 + 외부 스케줄러

입력은 단축어가 HTTP로 호출하는 엔드포인트가 받고, 정해진 시각 실행(메일 선별, 보고)은 같은 서비스의 별도 엔드포인트를 외부 스케줄러가 호출하는 방식이다. 이렇게 하면 호스팅 위치(서버리스, 개인 서버 등)에 설계가 묶이지 않는다. 대안인 상시 실행 프로세스는 개인 용도에 운영 부담이 크다.

### 3. 벨루 쓰기는 벨루 백엔드 API를 거친다

벨루가 쓰는 서버 키는 모든 테이블에 대한 전권이다. 이를 비서가 보관하는 것은 위험이 과하다. 비서 전용 계정으로 로그인해 세션을 얻고, 일반 사용자와 같은 태스크 API로 쓴다. 이렇게 하면 검증 로직이 벨루 한 곳에 남고, 비서가 잡을 수 있는 범위가 해당 사용자 계정으로 제한된다. 대안(Supabase 직접 쓰기)은 구현이 단순하지만 위 이유로 후순위이며, 로그인 방식 때문에 API 경로가 막히면 대체로 사용한다(열린 질문 2).

### 4. 처리 이력은 장부와 별도 저장소에 둔다

"어떤 출처를 이미 처리했는가"는 벨루 태스크에 의존하지 않고 비서 자체의 작은 저장소(출처 ID, 처리 시각, 결과)에 둔다. 사용자가 비서가 만든 태스크를 지워도 표식이 함께 사라지기 때문에, 벨루만 보면 같은 메일을 다시 처리해 되살리게 된다(`ledger-task-sync` 스펙). 표식(메모의 비서 생성 표시와 출처 ID)은 사람이 벨루에서 눈으로 구분하기 위한 용도로 함께 유지한다.

### 5. 시각은 메모에 적고 마감일 필드에는 날짜만 둔다

벨루의 `deadline`이 텍스트이고 시각 필드가 없어, 마감일은 `YYYY-MM-DD`로 정규화해 기존 화면 표시와 호환시키고 시각은 메모에 둔다. 벨루 스키마 변경은 하지 않는다. 해석이 자주 틀려 불편해지면 벨루에 구조화된 시작 시각 컬럼을 추가하는 것을 별도 change로 제안한다.

### 6. 위임 정책은 도구 노출로 강제한다

프롬프트로 "하지 마"라고 쓰는 것은 우회될 수 있다. 위임 단계에 맞춰 모델이 호출할 수 있는 도구 자체를 제한한다: 읽기 도구는 항상, 태스크 추가 도구는 알리고 수행 단계로, 수정·삭제·발송은 제안만 기록하는 도구로만 제공하고, 금지 단계의 도구는 아예 제공하지 않는다(`delegation-policy` 스펙).

### 7. 보고는 출력 전용, 수정은 장부에서

카톡은 답장을 받을 수 없으므로 승인 대기 방식의 확인 흐름을 설계하지 않는다. 확인이 필요한 항목은 보고에 제안으로 싣고, 실제 수정은 사용자가 벨루에서 직접 한다.

### 8. 런타임과 호스팅: TypeScript(Node.js 24) + Vercel 함수, 스케줄은 Vercel Cron

운영할 서버를 두지 않고, 단축어가 호출할 공개 HTTPS 주소를 바로 얻기 위해 정했다. 입력·보고는 `api/` 아래 함수가 받고, 정해진 시각 실행은 Vercel Cron이 같은 프로젝트의 함수 주소를 호출한다. 대안은 Python(FastAPI)을 직접 운영하는 서버에 두는 것이었으나, 서버 접근과 HTTPS 설정 부담이 커서 채택하지 않았다.

- 서버리스라 로컬 파일에 상태를 둘 수 없으므로, 결정 4의 처리 이력 저장소는 이미 쓰는 Supabase에 비서 전용 테이블로 둔다. 어느 Supabase 프로젝트에 둘지는 2.2에서 확정한다.
- Cron은 UTC 기준이고, 무료 플랜은 하루 1회에 시각 정밀도가 낮다고 알고 있다. 보고를 정확한 분에 보낼 필요는 없으므로 수용하되, 1.1의 검증에서 실제 동작을 확인한다.
- 비서 함수들은 벨루와 HTTP로만 통신하므로 벨루의 언어(Python)와 맞출 필요가 없다.

### 9. 모델 공급자는 Gemini API, 호출은 한 모듈 뒤에 둔다

모델 호출은 `src/model.ts` 하나의 좁은 인터페이스(텍스트·이미지 입력을 받아 구조화 결과를 돌려주는 함수, 도구 호출 루프) 뒤에 둔다. 입력 해석, 메일 선별, 보고 문장 다듬기는 이 인터페이스만 부르고 공급자 SDK를 직접 import하지 않는다. 이렇게 하면 공급자를 바꾸거나 테스트에서 가짜 모델을 끼우기 쉽다. 구체 SDK(공식 Google SDK 또는 Vercel AI SDK)와 모델 이름은 3.2에서 최신 문서를 확인해 정하며, 접근 방식이나 스펙은 바뀌지 않는다. 모델 이름은 코드에 박지 않고 환경 변수로 받는다.

## Risks / Trade-offs

- [모델이 날짜를 잘못 해석해 틀린 태스크가 쌓임] → 추정 내역을 응답과 보고에 항상 명시하고, 사용자가 장부에서 삭제하면 되살아나지 않게 한다. 처음에는 비서 표식으로 쉽게 골라낼 수 있게 한다.
- [메일·입력 내용이 외부 모델 API로 전송됨, 다른 사람의 메시지가 섞일 수 있음] → 키워드 필터를 통과한 메일만 본문을 읽고, 화면 이미지 입력은 사용자가 의도해서 보낸 경우로만 한정한다.
- [단축어 엔드포인트가 인터넷에 노출됨] → 공유 비밀값 검증, 거부 시 모델 호출 없음(`quick-capture-intake` 스펙).
- [카카오 토큰이 만료되어 보고가 조용히 끊김] → 실패를 기록하고 다음 실행에서 복구를 시도한다. 사용자가 보고가 안 온 것을 알아챌 수 있어야 하므로 실패 기록의 확인 경로를 둔다.
- [벨루 로그인 방식이 비브라우저 클라이언트에 맞지 않을 수 있음] → 열린 질문 2, 대체 경로는 결정 3에 있다.
- [비서가 만든 태스크를 사용자가 읽고 "내가 쓴 확정 일정"으로 오해함] → 표식으로 구분하고 보고에 항상 "비서가 추가"로 표시한다.

- [Gemini API의 무료 등급은 입력이 제품 개선에 쓰일 수 있다고 알고 있음(미확인). 메일 본문과 카톡 화면에는 다른 사람의 정보가 섞임] → 3.2 전에 사용 중인 요금제의 데이터 사용 조건을 공식 문서로 확인하고, 해당된다면 유료 등급을 쓰거나 이미지 입력 범위를 줄인다.

## Migration Plan

신규 구성이라 이전 대상이 없다. 롤백은 비서 표식이 붙은 태스크를 벨루에서 골라 삭제하고, 스케줄러 호출과 단축어를 끄는 것이다.

## Open Questions

답이 나와도 스펙, 접근 방식, 작업 분할이 바뀌지 않는 것만 남긴다.

1. **화면 캡처 동작**: 단축어의 화면 캡처가 Siri 음성 실행 시 Siri 화면을 함께 찍는지 확인한다(5분 실험). 결과에 따라 입력 방식(음성, 뒷면 탭, 복사)의 비중만 정해진다.
2. **벨루 비브라우저 로그인**: 비서 전용 계정이 쿠키 세션을 얻는 방법(비밀번호 로그인 여부)을 구현 전에 확인한다. 막히면 결정 3의 대체 경로를 쓴다.
3. **메일 키워드 목록과 조회 기간**: 실제 최근 한 달 메일로 시험해 정한다.
4. **보고 시각**: 언어/런타임과 호스팅은 결정 8로 정했다. 시각은 Cron 정밀도를 확인한 뒤(1.1) 정한다.
5. **마감 교차 검증**: 메일의 마감을 공식 웹 페이지로 확인하는 기능은 이번 범위에서 제외한다. 메일 선별이 안정되면 후속으로 검토한다.
