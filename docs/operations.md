# 운영 방법

## 구성

```
아이폰 단축어 --POST--> /api/intake      (해석 -> 벨루에 저장 -> 응답)
Vercel Cron  --매일--> /api/cron/daily   (메일 선별 -> 벨루에 저장 -> 아침 보고 -> 카톡)
```

- Cron은 UTC 기준 `0 22 * * *`, 즉 **한국 시간 07:00**이다. 무료(Hobby) 플랜은 하루 한 번만 돌릴 수 있고 정확한 분에 실행되지 않을 수 있다(정확도는 첫 예약 실행 로그로 확인한다).
- `/api/cron/ping`은 Cron 연결을 확인하려고 만든 임시 경로다. 첫 예약 실행이 로그에 찍히면 지운다.

## 환경 변수

| 이름 | 용도 | 필수 |
|---|---|---|
| `INTAKE_SECRET` | 단축어와 PC 입력 페이지(`/capture.html`) 인증. 바꾸면 폰 단축어도 같이 바꾼다([`desktop-capture.md`](desktop-capture.md)) | 예 |
| `CRON_SECRET` | Cron 호출 인증. 설정하면 Vercel이 호출 때 자동으로 `Authorization: Bearer`를 붙인다 | 예 |
| `GEMINI_API_KEY`, `GEMINI_MODEL` | 모델 호출. 기본 모델(텍스트와 일반 화면 캡처). 지금은 `gemini-3.8-flash` | 예 |
| `GEMINI_HIGH_MODEL` | 이미지가 **손글씨로 판단되면 다시 읽는** 큰 모델(`?quality=high`로 강제하는 요청에도 쓴다). 지금은 `gemini-3.1-pro-preview`. 없으면 다시 읽지 않고 기본 모델만 쓴다 | 아니오 |
| `VELOO_BASE_URL`, `VELOO_USERNAME`, `VELOO_PASSWORD` | 벨루 로그인. 전용 계정을 권장한다 | 예 |
| `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN` | Gmail 읽기 | 매일 실행에 필요 |
| `MAIL_KEYWORDS` | 메일 선별 키워드(쉼표 구분) | 매일 실행에 필요 |
| `MAIL_LOOKBACK_DAYS` | 조회 기간(기본 2일) | 아니오 |
| `KAKAO_REST_API_KEY`, `KAKAO_CLIENT_SECRET`, `KAKAO_REFRESH_TOKEN` | 카톡 나에게 보내기 | 매일 실행에 필요 |
| `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` | 처리 이력·토큰 저장소 | 사실상 필요(아래) |

항목 이름만 `.env.example`에 있다. 실제 값은 `.env.local`(로컬)과 Vercel 환경 변수에만 둔다.

**저장소(Supabase)가 없으면** 처리 이력이 호출마다 사라진다. 그러면 메일 중복 방지가 조회 기간(2일)에만 기대게 되고, 카카오 토큰이 갱신되어 새 리프레시 토큰이 나와도 저장되지 않는다. 보고에 "저장소가 설정되지 않아…"라는 참고 문구가 붙는다. 저장소를 쓰려면 Supabase SQL 편집기에서 `supabase/assistant.sql`을 한 번 실행하고 두 환경 변수를 넣는다.

저장소 점검: `npm run store:check`는 실제 Supabase에 기록·중복 판별·조회·상태 저장을 시험하고 시험 데이터를 지운다(`.env.local`의 값을 쓴다).

**지금 구성의 주의점**: 비서 테이블이 폴리오와 같은 Supabase 프로젝트에 있고, 서버가 쓰는 키는 그 프로젝트의 관리자 키다. 비서 서버가 뚫리면 폴리오 데이터에도 닿는다. 별도 프로젝트로 옮기려면 새 프로젝트에서 `supabase/assistant.sql`을 실행하고, `.env.local`과 Vercel의 `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`만 바꿔서 다시 배포한다(이력은 새로 시작된다).

## 아침 보고에 나오는 것

위에서부터 중요한 순서이고, 카톡 한 통(200자)을 넘으면 다음 통으로 이어지며 최대 3통까지 보낸다. 분량이 모자라면 아래쪽부터 줄이고 `…외 N건 생략`을 남긴다.

| 줄 | 의미 |
|---|---|
| `⚠ 실패:` | 처리에 실패한 것 |
| `확인:` | 마감이 달라 보이는 기존 태스크(수정 제안), 마감이 불확실한 메일 |
| `먼저 1) … — 이유` | **오늘 먼저 할 일 Top 3**. 마감·우선순위·밀린 정도로 순위를 매기고 모델이 고른 한 줄 이유 |
| `오늘:` | 오늘 마감인 미완료 태스크 |
| `밀린 일:` | 마감이 지난 미완료 태스크와 **며칠째**인지 |
| `임박:` | 내일부터 7일 안에 마감인 미완료 태스크와 **며칠 후**인지 |
| `메일 마감:` | 메일에서 가져온 일정 중 마감이 가까운 최대 3건 |
| `방치:` | 마감 없이 생성된 지 14일 이상 된 미완료 태스크와 며칠째인지(최대 2건) |
| `폴리오:` | 이번 주에 폴리오에 새로 들어온 논문 수와 제목(최대 3개) |
| `지난주:` | 지난주 완료·생성·밀린 수(벨루 주간 리뷰) |
| `추가:` | 지난 보고 이후 비서가 벨루에 만든 태스크(같은 것은 `×2`처럼 합침) |
| `할 일:` | 마감이 없는 미완료 태스크 |
| `참고:` | 저장소 미설정, 지난주 통계나 폴리오를 읽지 못함 등 |

- 각 구역은 최대 5개(메일 마감은 3, 방치는 2)까지 보이고 넘으면 `외 N건`으로 남은 개수를 알린다. `먼저`나 `추가`에 나온 태스크는 다른 구역에 되풀이하지 않는다(오늘 마감은 항상 보여 준다).
- **삭제된 태스크는 나오지 않는다.** 처리 기록과 벨루의 현재 목록을 대조해서 지금 벨루에 없는 태스크는 `추가`와 `확인`에서 뺀다.
- 순위를 매기는 모델이 실패하면 규칙 순위와 규칙 이유(`급함 · 4일 남음` 등)로 대신한다.
- **폴리오의 새 논문**은 비서가 처음 본 시점으로 센다. 폴리오에는 "처음 저장한 시각"이 없고 동기화 시각이 정보를 다시 가져올 때마다 바뀌기 때문이다. 처음 실행할 때는 동기화 시각이 최근 7일 안인 것만 이번 주로 센다. 폴리오는 같은 Supabase 프로젝트의 `folio_papers` 테이블을 **읽기만** 한다.
- 마감은 `YYYY-MM-DD` 형식이어야 날짜로 읽힌다(벨루 화면에서 날짜를 고르면 그 형식으로 저장된다).

## 환경 변수를 Vercel에 넣기

```
vercel env add NAME production --sensitive    # 값은 프롬프트에 붙여 넣는다
vercel env add NAME production --sensitive --force   # 이미 있는 값을 바꿀 때
```

환경 변수는 새 배포부터 적용된다. 바꾼 뒤에는 `vercel deploy --prod`를 다시 한다.

## 매일 실행 확인과 시험

```
vercel crons list                       # 등록된 Cron
vercel crons run /api/cron/daily        # 지금 한 번 실행(실제로 카톡이 간다)
vercel logs --no-follow --limit 20 --expand
```

카톡을 보내지 않고 보고 내용만 보려면 시험 호출을 쓴다. **아무것도 쓰지 않는다**(벨루, 처리 이력, 보낸 시각 모두). 추가될 태스크는 `(예정, 저장 안 함)`으로 표시된다. 다만 메일 내용은 실제로 Gemini에 전송된다.

```
curl -H "Authorization: Bearer $CRON_SECRET" "https://personal-secretary-kappa.vercel.app/api/cron/daily?dry=1"
```

## 비서가 만든 태스크 찾기·지우기

**벨루 메모에는 내부 표식을 남기지 않는다.** 어떤 태스크를 비서가 만들었는지는 처리 기록(Supabase)의 태스크 번호로 안다. 벨루에서 지금 어떤 것이 비서가 만든 태스크인지 보려면 아래를 실행한다(읽기 전용).

```
npm run assistant:tasks
```

번호, 만든 경로(메일 또는 폰 입력), 이름, 마감, 완료 여부가 나오고, 이미 지워진 것의 개수도 함께 보여 준다. 찾은 태스크는 벨루에서 직접 지운다. **지워도 같은 출처에서 다시 만들어지지 않고 보고에도 나오지 않는다**(처리 기록이 따로 있고, 보고는 벨루의 현재 목록과 대조한다).

예전에 만든 태스크 일부에는 메모에 `[비서:…]` 표식이 남아 있을 수 있다. 보고에서는 가려지고 비서는 그것도 비서가 만든 것으로 알아본다. 벨루에서 보이는 표식이 거슬리면 메모에서 직접 지우면 된다.

## 끄기와 되돌리기

1. 아침 보고를 멈춘다: `vercel.json`의 `crons`에서 `/api/cron/daily` 항목을 지우고 재배포한다.
2. 단축어를 멈춘다: 폰에서 단축어를 지우거나 `INTAKE_SECRET`을 바꾼다(서버와 단축어의 값이 다르면 401로 거부된다).
3. 비서가 만든 태스크를 지운다: `npm run assistant:tasks`로 비서가 만든 태스크를 확인하고 벨루에서 지운다.

## 토큰 수명

- 카카오 리프레시 토큰: 약 60일. 갱신하면 새 토큰이 같이 올 수 있고, 저장소가 있으면 자동으로 저장해서 이어 쓴다.
- Gmail 리프레시 토큰: OAuth 동의 화면이 "테스트" 상태이면 7일 뒤에 만료될 수 있다고 알려져 있다. 개인용이면 "프로덕션으로 게시"로 바꾼다. 만료되면 보고에 `메일 선별 실패: Gmail token refresh failed -> 400 invalid_grant`가 올라온다.
- 벨루 세션: 30일. 만료되면 자동으로 다시 로그인한다.

## 실패가 보이는 곳

모든 실패는 아침 보고 맨 위에 `⚠ 실패:`로 올라온다. 보고 전송 자체가 실패하면 다음 보고에 "보고 전송 실패"와 함께 놓친 내용이 같이 온다.

| 보고의 문구 | 의미 |
|---|---|
| `벨루 읽기/쓰기 실패` | 벨루 서버에 닿지 않거나 로그인 실패 |
| `메일 선별 실패` | Gmail 인증 만료 등 |
| `보고 전송 실패` | 카카오 인증 만료 등 |
| `참고: 저장소가 설정되지 않아…` | Supabase 환경 변수 없음 |

## 예약 실행을 확인하는 법

- **Vercel 로그는 약 1시간만 보관된다**(무료 플랜). 아침 예약 실행이 돌았는지는 로그가 아니라 저장소의 `last_report_at`으로 확인한다(`assistant_state` 테이블, 보고가 성공했을 때만 갱신된다).
- 첫 예약 실행(2026-10-05)은 예약 07:00보다 **약 9분 늦은 07:09**에 돌았다. 무료 플랜의 Cron은 정해진 분에 실행되지 않고 그 시각 근처에서 실행된다.

## 알려진 제약

- 벨루가 인터넷에서 접속되지 않으면(서버가 꺼져 있거나 외부 포트가 닫힌 경우) 쓰기와 오늘 일정 읽기가 실패한다. 이때도 일정 해석과 보고는 동작하고 실패가 보고에 올라온다.
- 비서는 벨루 태스크를 **만들기만** 한다. 수정·삭제·메일 발송 도구는 코드에 없다(`docs/delegation.md`).
